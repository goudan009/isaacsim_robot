# 测试报告协作规范

本规范约束本仓库所有测试报告的语言、结构、判定和原始证据归档方式。后续 agent 进行测试、
迁移或修复时，必须遵守本规范；不得自行创建按日期命名的结论报告。

## 1. 固定文件

| 测试类别 | 固定结论报告 | 原始证据目录 |
| --- | --- | --- |
| 阶段迁移与构建 | `reports/migration/stages_1_to_3.md` | 测试框架输出或批次原始目录 |
| 无传感器机器人控制 | `reports/performance/robot_control_performance.md` | `reports/performance/raw/robot_control_baseline/`、`robot_control_full/` |
| 机器人控制与四路相机负载探针 | `reports/performance/robot_control_performance.md` | `reports/performance/raw/robot_control_full/` |
| 空场景性能 | `reports/performance/empty_scene_performance.md` | `reports/performance/raw/empty_scene/` |
| 独立传感器 | `reports/sensors/sensor_validation.md` | `reports/sensors/raw/` |
| 双/三进程机器人传感器副本实验 | `reports/sensors/sensor_validation.md` | `reports/sensors/raw/<批次编号>/` |

同一类别只维护一份结论报告。每次运行只在该报告的“批次记录”中追加一个简短批次，
不得复制整段测试方法、历史结论或调试日志。

## 2. 语言与状态

- 报告正文、表头、结论和说明使用中文。
- 代码、包名、ROS 话题、消息类型、配置键和命令保留原始英文，并使用反引号标记。
- 对外结论只允许使用：`通过`、`未通过`、`条件通过`、`测试异常`、`未运行`、`停止`。
- 程序内部状态码可写入原始 JSON；Markdown 中如需保留，只能写作“内部状态码：`...`”，
  不得把英文状态码当作报告结论。

## 3. 批次元数据

每个批次必须包含下列字段。缺失字段的测试只能记为“测试异常”或“未运行”。

| 字段 | 规则 |
| --- | --- |
| 批次编号 | `YYYYMMDD-HHMMSS-类别-执行者`；执行者使用 agent 名称或 `manual` |
| 执行时间 | 使用 Asia/Shanghai 的绝对时间 |
| 执行者 | 人员或 agent 标识；未知时写“未填写” |
| 软件版本 | Git 提交、工作区状态或“未记录” |
| 测试范围 | 明确是否含机器人、控制器、传感器、RViz |
| 配置 | physics、render、控制频率、关键 profile 和 launch 参数 |
| 原始证据 | JSON、启动日志、必要时 rosbag/截图的相对路径 |

## 4. 统一批次模板

```markdown
### 批次：<批次编号>

| 字段 | 内容 |
| --- | --- |
| 执行时间 | <YYYY-MM-DD HH:MM:SS +08:00> |
| 执行者 | <agent 或 manual> |
| 版本 | <Git 提交 / 未记录> |
| 测试范围 | <明确组件和排除项> |
| 配置 | <关键频率、profile、launch 参数> |
| 功能结论 | <通过 / 未通过 / 测试异常 / 未运行> |
| 实时结论 | <通过 / 未通过 / 条件通过 / 未运行> |

| 指标 | 通过线 | 实测值 | 判定 |
| --- | --- | ---: | --- |
| <指标 1> | <阈值或不设线> | <数值> | <通过/未通过/仅记录> |

结论：<最多三句；说明未通过项和下一步。>

原始证据：`<相对路径>`。
```

## 5. 测评线

### 5.1 无传感器机器人控制

| 指标 | 当前通过线 | 用途 |
| --- | --- | --- |
| 仿真时间回退 | `0` | 时间窗口有效性 |
| 控制器状态 | 所需控制器均为 `active` | 功能前置条件 |
| 底盘响应 | 轮速 > 0，里程计位移 > 0 | 底盘功能验收 |
| 升降、头部、左右臂 | 每个目标关节位移均不低于测试阈值 | 完整控制功能验收 |
| `/joint_states` | 不低于 `90 Hz` | 当前公共状态发布目标 |
| physics step rate | 不低于 `120 Hz` | 实时物理目标 |
| RTF | 不低于 `1.0` | 实时仿真目标 |

功能结论与实时结论必须分开：例如关节能动作但 physics 低于 `120 Hz`、RTF 低于 `1.0`，
应写“功能通过、实时未通过”，不能笼统写“通过”。

### 5.2 空场景性能

| 指标 | 当前通过线 |
| --- | --- |
| 仿真时间回退 | `0` |
| 重复时间戳 | `0` |
| RTF | 仅记录；推荐不低于 `1.0` |
| physics step rate | 仅记录；用于同配置负载对比 |

空场景只用于基线比较，不能替代机器人控制或传感器验收。

### 5.3 RealSense 与 MID360

| 指标 | 当前通过线 |
| --- | --- |
| RealSense 图像、深度、相机内参、TF | 话题存在、类型正确、时间戳单调 |
| RealSense 四路图像 | 当前基线每路约 `30 Hz`，队列丢弃为 `0` |
| 双/三进程机器人传感器副本最低采集 | 主控制进程按无传感器控制线验收；相机副本每路 RGB/Depth 不低于 `20 Hz`；MID360 联合整机测试不低于 `8 Hz` 且非空；必须记录状态快照 P99/max 时延 |
| 双进程机器人相机副本正式目标 | 副本每路 RGB/Depth 不低于 `29 Hz`；还需完成状态、对象和时间一致性验收 |
| 控制关键路径 gap | P99 不高于 `13.333 ms`，最大值不高于 `22.222 ms` |
| MID360 performance 档 | CustomMsg 不低于 `10 Hz`，逐点时间有效 |
| MID360 approx 档 | 频率只记录，不得把 raw 频率写成 CustomMsg 频率 |
| 动态外参与 ATE/RPE | 未完成前只能写“未运行” |

说明：`8 Hz` 只适用于“完整机器人 + 四路相机 + MID360”的三进程联合准入线，
对应整机实际接收的非空 PointCloud2 墙钟频率。独立 MID360 性能基线仍按 `10 Hz`
记录和判定；raw PointCloud2、重打权威时钟后的输出和 Python `CustomMsg` 必须分别统计。
重打包程序同时记录总运行窗口频率和首条至末条消息的有效窗口频率，报告判定使用有效窗口频率。

## 6. 原始证据规则

- 新测试使用独立批次目录：`reports/<类别>/raw/<测试项>/<批次编号>/`。
- 每个批次至少包含 `result.json` 和 `launch.log`；有图像或可视化证据时再增加截图或录包。
- 原始证据不可覆盖其他批次；“最新”指针或汇总 JSON 可覆盖，但不得替代批次证据。
- 失败重试保留在原始证据中；结论报告只汇总最终有效批次，并在必要时用一句话说明失败原因。

## 7. Agent 写入流程

1. 先读取本规范和对应固定结论报告。
2. 运行测试并写入独立批次原始目录。
3. 调试重试只写入原始证据目录；确认后的有效批次才按统一模板追加。`robot_control_full_performance.py` 需显式传入 `--append-report`。
4. 更新报告顶部“当前结论”时，必须注明采用的最新有效批次编号。
5. 不得把独立传感器或双/三进程传感器副本实验写成阶段 4 正式产品化结果；阶段 5 入口通过后，
   仍须单独记录正式启动链路、动态外参、时间一致性和重复稳定性验收。

阶段 4 未授权时始终保持“停止”；阶段 5 的性能入口通过不等于阶段 4 产品化验收通过。
